# CartStock — inventory holds with atomic cart edits

Build a compact in-memory JavaScript ES module in `src/stockroom.js`. Export `createStockroom({stock, now=0})` and `restoreStockroom(snapshot)`. All methods may be synchronous or asynchronous; callers may await every call. Inputs and results are JSON values. Use no wall clock, persistence, network, external dependency, or background timer. Add a short README usage example.

API: `reserve({id,owner,items,ttl})`, `amend({id,owner,version,items,ttl?})`, `confirm({id,owner,version})`, `cancel({id,owner,version})`, `get(id)`, `availability()`, `advance(time)`, `snapshot()`.

1. `stock` is a nonempty object mapping SKU to nonnegative safe integer on-hand quantity. SKU matches `/^[A-Za-z][A-Za-z0-9_-]{0,31}$/`; `constructor` is a valid SKU. `items` is a nonempty SKU-to-positive-safe-integer object containing only known SKUs. IDs and owners are strings of length 1–64, used literally without trimming. Logical `now` is a nonnegative safe integer. `ttl` is a positive safe integer and `now+ttl` must be safe whenever a new deadline is computed. Versions supplied to commands are positive safe integers. Invalid shapes/scalars throw Error with `code='INVALID'`; an unknown SKU throws `UNKNOWN_SKU`. No need to define precedence for several unrelated invalid fields.
2. `reserve` atomically creates a `held` reservation at version 1 and `expiresAt=now+ttl`, provided every item fits current availability. Insufficient quantity throws `INSUFFICIENT` with no state change. A view has exactly `{id,owner,items,expiresAt,state,version}`. Every successful reservation-changing method returns its new detached view. `get(id)` returns that same detached view; missing ID throws `UNKNOWN_RESERVATION`. IDs are never removed or reused.
3. Reserve is idempotent by ID and its **initial** request `{owner,items,ttl}`. The order of keys in `items` is irrelevant. Repeating the same initial request returns the **current** reservation view without changing version, inventory or expiry—even after an amend, confirm, cancel, expiry, or restore. Any different initial-request value using that ID throws `ID_CONFLICT`. A replay at a later logical time does not extend the original expiry. Replay validates the literal fields but does not recompute a deadline or recheck capacity.
4. `amend`, `confirm` and `cancel` require the existing owner and `held` state, then an exact version. For otherwise valid inputs, check owner **before state and version**: wrong owner throws `FORBIDDEN`; correct owner on a terminal state throws `STATE`; held with stale version throws `VERSION_CONFLICT`. Successful commands increment version by exactly 1. Failed commands change nothing. `amend` replaces the entire item map and credits its old hold before checking capacity. It is all-or-nothing across every SKU, version and expiry. If ttl is omitted, keep the old expiry; if supplied, replace expiry with `now+ttl`. An identical successful amend still increments version.
5. `availability()` returns every SKU's on-hand quantity minus quantities in **held** reservations. `confirm` reduces on-hand quantities by the held items and changes state to `confirmed`, so availability immediately before/after confirm is equal. `cancel` changes state to `cancelled`, releasing the hold without changing on-hand stock. Terminal reservations retain their items and expiresAt in their views; confirm/cancel on a terminal reservation is not an idempotent command and follows STATE above.
6. Only `advance(time)` changes logical time. It requires a nonnegative safe integer >= current time; otherwise throw `INVALID_TIME` without state changes. Before returning it expires all held reservations with `expiresAt <= time`, changing state to `expired` and incrementing each version once. Return exactly `{now:time,expired:[ids]}`, ordered by expiry then ID using JavaScript string comparison. Repeating advance at the same time does not expire them again. Terminal reservations never expire. No other method implicitly advances or expires anything.
7. `snapshot()` returns exactly `{schemaVersion:1,now,onHand,reservations}`. `onHand` is current stock after confirmed purchases. Reservations are sorted by ID using JavaScript string comparison; each entry contains its six view fields plus `initialRequest:{owner,items,ttl}` for reserve replay. Snapshot/JSON-clone/restore preserves every reservation, version, terminal history, expiry, stock and initial replay request. Original and restored copies evolve independently. Only this implementation's produced snapshots are required restore inputs.
8. Mutating submitted stock/items, returned views, availability maps or snapshots must never mutate internal state. Do not add behaviors not specified here. Tests should exercise public API sequences, especially failed multi-SKU edits, repeated requests after amendments, owner/version precedence, exact expiry boundaries, confirm/release accounting and restore. Undefined behavior is not a reason to invent an acceptance assertion.
