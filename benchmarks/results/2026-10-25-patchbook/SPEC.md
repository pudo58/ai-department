# PatchBook — atomic JSON edits with historical replay

Implement a small in-memory JavaScript ES module `src/patchbook.js`. Export exactly `createPatchBook(initial)` and `restorePatchBook(snapshot)`. A book has `read()`, `apply({id,baseRevision,ops})`, `snapshot()`. Calls may be sync or async; callers await each. Add a short README example. No dependency, filesystem, network, wall clock, background task, eval or dynamic code execution. Only documented behavior is required; do not invent behavior for unspecified inputs.

1. A JSON value is null, boolean, string, finite number, dense array of JSON values, or plain object (Object.prototype or null prototype) with JSON values in its own enumerable string properties. Reject undefined, NaN/Infinity, holes and cycles with Error code `INVALID`. Root null is valid. `createPatchBook(initial)` clones the initial value and starts revision 0. `read()` returns exactly `{revision,document}`, detached. All submitted values, returned reads/receipts/snapshots and restored instances must remain independent of internal state.
2. `apply` requires a non-null plain object with exactly id, baseRevision, ops. ID is a literal string length 1–64, without trimming. baseRevision is a nonnegative safe integer. ops is a dense array of 1–32 operation objects. Operation shapes are exact: `{op:'put',path,value}`, `{op:'remove',path}`, `{op:'check',path,value}`, `{op:'move',from,path}`. path/from must be strings; value must be JSON. Reject malformed outer request, null request/operation, missing/extra field, unknown op or invalid scalar/value with `INVALID`. No precedence is required between unrelated malformed fields.
3. Paths use THIS grammar (not an external standard): empty string is root; every other path begins `/`, then segments separated by `/`. In each segment `~0` decodes to `~` and `~1` to `/` in a single pass; any other/lone tilde and any nonempty path without leading `/` throws `PATH_SYNTAX`. Empty segments and keys `__proto__`, `constructor`, `prototype` are valid literal object keys and must never access inherited properties or change prototypes. On objects, all intermediate keys must exist as OWN properties or throw `NOT_FOUND`. Traversing a primitive/null throws `TYPE`. On arrays, an index must be canonical decimal `0` or a nonzero digit followed by digits, and be a safe integer: invalid spelling or out-of-range throws `INDEX`. Intermediate indices must exist; `-` is allowed ONLY as the final array destination of put/move, meaning append. Object segments such as `01` or `-` are ordinary keys.
4. `put` at root replaces the document. In an object, put inserts/replaces the final own key (without creating missing ancestors). In an array, put INSERTS at indices 0..length (or appends for `-`), shifting later items; it does not overwrite an item. `remove` requires an existing own key or array index 0..length-1; root removal replaces the document with null. `check` compares the value at its path with the submitted value: JSON deep equality ignores object key order, preserves array order, and treats -0 as 0. Unequal values throw `TEST_FAILED`; missing paths use the normal lookup errors. Check does not alter document content.
5. `move` first resolves an existing source value. Same decoded source and destination is a successful no-op (source must still exist). A proper decoded-segment prefix from source to destination throws `MOVE_INTO_SELF` BEFORE removing anything; `/a` is not an ancestor of `/ab`, while root is an ancestor of every non-root path. Otherwise remove source, then resolve destination on the POST-REMOVAL document and insert/replace using put rules. Thus moving `/items/1` to `/items/3` in a four-item array is valid and yields the old second item at the end; an index valid before removal can be invalid afterwards. A failed destination rolls back both the removal and any earlier operation in the batch. Moving a nested value to root is allowed.
6. Precedence and transaction rules: first validate ALL request/operation shapes, JSON values and path syntaxes, without resolving paths. Next handle successful ID history (rule 7), then compare baseRevision to current revision; mismatch throws `REVISION_CONFLICT` before path resolution. Then execute operations sequentially on a private candidate. First operation failure aborts everything: document, revision and receipt history stay unchanged; a failed new ID is reusable. A successful batch increments revision exactly once, including check-only or same-path-move batches, and returns a detached receipt exactly `{id,revision,document}` showing its committed document. No intermediate state becomes visible.
7. Successful IDs are permanent. Replay matches the INITIAL `{baseRevision,ops}` structurally, ignoring object key order but preserving arrays and literal IDs. An exact repeat returns the SAME HISTORICAL receipt saved for that ID, even after later commits or restore, without checking current revision, resolving old paths, incrementing revision or changing history. Any different baseRevision/ops using that ID throws `ID_CONFLICT`, ahead of revision/path-resolution errors. Invalid shapes and pointer syntax are still rejected before ID history. Do not return the current document as an old receipt or mutate stored requests while executing their values.
8. `snapshot()` returns exactly `{schemaVersion:1,revision,document,receipts}`. receipts is an array in commit order, each entry exactly `{id,baseRevision,ops,result}` where result has exactly the three receipt fields `{id,revision,document}`. Store initial request ops and historical committed result, not the latest document for every entry. Snapshot/JSON-clone/restore preserves all content, revision and replay receipts. Only this implementation's produced snapshots are required restore inputs; nevertheless a null/non-object outer restore argument must throw `INVALID`. Do not infer validation rules for hand-authored/corrupted snapshot internals. Returned snapshots and both original/restored instances evolve independently.

Examples: starting `{items:['a','b','c','d']}`, one batch `move /items/1 -> /items/3` commits `{items:['a','c','d','b']}`. Starting `{a:1}`, a batch `put /b = 2`, `check /a = 9` fails `TEST_FAILED` and leaves revision 0/document `{a:1}` with no receipt. Commit request X adding b, then request Y removing a: replay X returns its earlier `{a:1,b:2}` document and earlier revision, while `read()` stays at Y. A null apply request is invalid; a null initial document is valid.
