# TicketFlow — ticket states, reopening, escalation and merging

Implement `src/tickets.js` as an in-memory support-ticket workflow. Export `createTickets({ now = () => 0, reopenWindow = 100, maxReopens = 2, escalateAfter = 50 } = {})`. `now` is a function returning the current time as a nonnegative safe integer (minutes) that never decreases; the service never reads a wall clock. `reopenWindow` and `escalateAfter` are positive safe integers and `maxReopens` is a nonnegative safe integer (`INVALID_INPUT` otherwise). Methods are synchronous, and callers may also `await` them. Inputs and results are plain JSON values.

The service exposes `create({ id, subject, priority = 'normal' })`, `assign(id, agent)`, `wait(id)`, `customerReply(id)`, `resolve(id)`, `reopen(id)`, `close(id)`, `merge(sourceId, targetId)`, `get(id)` and `list({ status, assignee } = {})`.

1. Errors are `Error` objects with a string `code`. For `create`, `id` and `subject` must be nonempty strings and `priority` one of `low`, `normal`, `high`, `urgent` (`INVALID_INPUT`); an `id` that was ever used is taken (`ID_TAKEN`). Any other method fails with `UNKNOWN_TICKET` for an unknown id, and `assign` needs a nonempty string `agent` (`INVALID_INPUT`). A failed call changes nothing.
2. A new ticket has status `open`, no assignee and `reopenCount` 0. The statuses are `open`, `assigned`, `pending`, `resolved`, `closed` and `merged`. Only the transitions below exist; any other call fails with `BAD_STATE`.
   - `assign(id, agent)` works from `open`, `assigned` and `pending`; the ticket becomes `assigned` with that assignee (assigning again replaces the assignee).
   - `wait(id)`: `assigned` → `pending`. `customerReply(id)`: `pending` → `assigned`, keeping the assignee.
   - `resolve(id)`: `assigned` → `resolved`, and the time of the call is remembered as `resolvedAt`.
   - `reopen(id)`: `resolved` → `assigned`, keeping the assignee and adding one to `reopenCount`. It fails with `REOPEN_LIMIT` when `reopenCount >= maxReopens`.
   - `close(id)`: `resolved` → `closed`.
3. A resolved ticket closes by itself: at `now() >= resolvedAt + reopenWindow` its status is `closed`, in `get`, in `list` and for every method. Before that moment it is still `resolved` and can be reopened. A ticket that was reopened and resolved again starts a new window from its new `resolvedAt`.
4. Escalation. A ticket that is not yet assigned when `now()` reaches `createdAt + escalateAfter` (`createdAt` is the time of `create`) is *escalated* from that moment on, and stays escalated for good, even if it is assigned later. A ticket that was assigned at any time before `createdAt + escalateAfter` is never escalated by this rule. An escalated ticket's `effectivePriority` is its `priority` raised by one level (`low` → `normal` → `high` → `urgent`, and `urgent` stays `urgent`); otherwise `effectivePriority` equals `priority`.
5. `merge(sourceId, targetId)` folds a ticket into another. `sourceId` and `targetId` must differ (`SAME_TICKET`); both must be `open`, `assigned` or `pending`, otherwise `BAD_STATE`. The source becomes `merged` and gets `mergedInto: targetId`; it cannot change status again. The target's `priority` becomes the higher of the two priorities, and the target is escalated from then on if either ticket was escalated at the moment of the merge. The target keeps its status and assignee.
6. A view is `{ id, subject, priority, effectivePriority, status, assignee, reopenCount }` with `assignee` equal to `null` when there is none, plus `mergedInto` only for merged tickets. `get(id)` returns the view as of `now()`. Every method that changes a ticket (`create`, `assign`, `wait`, `customerReply`, `resolve`, `reopen`, `close`) returns the view of that ticket after the change, and `merge` returns the view of the target after the merge.
7. `list({ status, assignee })` returns the views of the tickets that match every filter given (`status` one of the six statuses, otherwise `INVALID_INPUT`; `assignee` a string), as of `now()`. They are sorted by `effectivePriority` from `urgent` down to `low`, and tickets with the same `effectivePriority` by the order in which they were created.

Error precedence is specified only where stated above; do not test inputs that break several unrelated rules at once. No persistence, network, timers or cleanup is required. Keep the source compact, use the public API in tests, and do not add behavior beyond this contract.
