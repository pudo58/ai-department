# RoomBookings — holds, confirmations and cancellations on half-open time intervals

Implement `src/bookings.js` as an in-memory room booking service. Export `createBookings({ rooms = [], holdTtl = 100, now = () => 0, maxDuration = 480 } = {})`. `rooms` is an array of unique nonempty room names. `now` is a function returning the current time as a nonnegative safe integer (minutes); the service never reads a wall clock. All times are nonnegative safe integers. Methods are synchronous, and callers may also `await` them. Inputs and results are plain JSON values.

The service exposes `hold({ id, room, start, end })`, `confirm(id)`, `cancel(id)`, `get(id)` and `list(room, { from, to } = {})`.

1. Errors are `Error` objects with a string `code`. `createBookings` throws `INVALID_INPUT` when `rooms` is not an array of unique nonempty strings, or `holdTtl` or `maxDuration` is not a positive safe integer. For `hold`: `id` must be a nonempty string (`INVALID_INPUT`); `room` must be one of `rooms` (`UNKNOWN_ROOM`); `start` and `end` must be nonnegative safe integers with `start < end` (`INVALID_INTERVAL`); `end - start` must not exceed `maxDuration`, and exactly `maxDuration` is allowed (`TOO_LONG`); `start` must not be before `now()`, and `start === now()` is allowed (`IN_THE_PAST`). An `id` that was ever used, even by a booking that was cancelled or expired, is taken forever (`ID_TAKEN`).
2. Intervals are half-open: `[start, end)`. Two intervals overlap when `a.start < b.end && b.start < a.end`, so intervals that only touch (`[0, 10)` and `[10, 20)`) do not overlap. Within one room, a hold that overlaps an active booking is refused with `CONFLICT` and changes nothing. Different rooms never conflict. Active bookings are holds that have not expired and confirmed bookings.
3. `hold` creates a booking with status `held`. A hold made at time `t` is active while `now() < t + holdTtl`. At `now() >= t + holdTtl` it has expired: its status is `expired`, it blocks nothing (another hold may take exactly its slot at that moment), and it no longer appears in `list`.
4. `confirm(id)` turns an active hold into a `confirmed` booking and returns its view. Confirming an already confirmed booking returns the same view unchanged. An expired hold fails with `HOLD_EXPIRED`, a cancelled booking with `ALREADY_CANCELLED`, an unknown id with `UNKNOWN_BOOKING`. A confirmed booking never expires, even after its end time has passed.
5. `cancel(id)` cancels a hold that is still active, at any time before it expires, and returns its view with status `cancelled`. A confirmed booking can be cancelled only while `now() < start`; at `now() >= start` it fails with `TOO_LATE` and stays confirmed. Cancelling an expired hold fails with `HOLD_EXPIRED`. Cancelling a booking that is already cancelled returns its view unchanged. An unknown id fails with `UNKNOWN_BOOKING`. A cancelled booking frees its slot at once.
6. A view is `{ id, room, start, end, status }`, with `status` one of `held`, `confirmed`, `cancelled`, `expired`, plus `expiresAt` (`t + holdTtl`) only while the status is `held`. `get(id)` returns the view as of `now()` or throws `UNKNOWN_BOOKING`.
7. `list(room)` returns the views of the active bookings of that room (held and confirmed), sorted by `start` ascending and then by `id` using JavaScript string comparison. With `{ from, to }` it returns only those overlapping the half-open window `[from, to)`; a missing `from` means 0 and a missing `to` means no upper limit. A window with `from >= to` or non-integer bounds fails with `INVALID_INTERVAL`; an unknown room with `UNKNOWN_ROOM`.

Error precedence is specified only where stated above; do not test inputs that break several unrelated rules at once. No persistence, network, timers or cleanup of old bookings is required. Keep the source compact, use the public API in tests, and do not add behavior beyond this contract.
