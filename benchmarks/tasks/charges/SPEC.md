# KeyedCharges — idempotent, concurrency-safe charging

Implement `src/charges.js` as an in-memory charge service. Export `createCharges({ accounts = {}, ttl = 1000, now = () => 0, authorize } = {})`. `accounts` maps an account name to its starting balance. `now` is a function returning the current logical time as a nonnegative safe integer; the service never reads a wall clock. `authorize`, when given, is `async ({ key, account, amount }) => boolean`. Every method returns a promise, and callers always `await` it. Inputs and results are plain JSON values.

The service exposes `charge({ key, account, amount })`, `deposit({ account, amount })` and `balance(account)`.

1. Errors are `Error` objects with a string `code`. `key` must be a nonempty string, otherwise `INVALID_INPUT`. `amount` must be a positive safe integer, otherwise `INVALID_AMOUNT`. An account that was not given in `accounts` is unknown: `UNKNOWN_ACCOUNT`. Starting balances must be nonnegative safe integers and `ttl` a positive safe integer, otherwise `createCharges` throws `INVALID_INPUT`. `balance(account)` returns the current balance or throws `UNKNOWN_ACCOUNT`. `deposit` adds `amount` to the account and returns the new balance.
2. A successful `charge` subtracts `amount` from the account and resolves to `{ chargeId, key, account, amount, balance, replayed: false }`, where `balance` is the account balance immediately after this charge and `chargeId` is a string that is unique among all charges the service ever made. A charge that would take the balance below zero fails with `INSUFFICIENT_FUNDS` and changes nothing.
3. A charge is idempotent by `key`. While the key of an earlier successful charge is live, repeating `charge` with the same `key`, `account` and `amount` does not subtract anything and resolves to the original result with the same `chargeId` and the original `balance` (the balance right after that first charge, not the balance now) but with `replayed: true`. The same `key` with a different `account` or `amount` while the key is live fails with `IDEMPOTENCY_MISMATCH` and changes nothing.
4. The key of a successful charge is live while `now() < t + ttl`, where `t` is the value of `now()` at the moment the money moved. At `now() === t + ttl` and later it has expired, and a charge with that key is a new, independent charge with a new `chargeId` (it replaces the old record for that key).
5. A failed charge never consumes its key. After `INSUFFICIENT_FUNDS` or `DECLINED`, the same key may be used again, even with a different account or amount, and is treated as a first use.
6. Input validation (rule 1) happens before anything else, so invalid calls never reach `authorize`. If `authorize` is present it is called exactly once per new attempt, before any money moves. A replay under rule 3 and a join under rule 8 are not new attempts and never call it. If it resolves to anything other than `true`, the charge fails with `DECLINED` and changes nothing. If it rejects, that same error is propagated and nothing changes.
7. Checking the balance and subtracting the amount happen together, after authorization has finished. Two concurrent charges with different keys on the same account, whose total exceeds the balance, must never overdraw it, however slowly `authorize` answers: the attempt whose authorization finishes first is charged first.
8. Concurrent calls with the same `key` are one attempt. While a charge for a key is in flight (its `authorize` has not yet finished), another call with the same key, account and amount joins it: `authorize` is not called again, and both calls observe the same outcome. If it succeeds, the first caller gets `replayed: false` and every joiner gets the same result with `replayed: true`. If it fails, every caller gets an error with the same `code`. A call joining with a different account or amount fails with `IDEMPOTENCY_MISMATCH` and does not disturb the attempt in flight.
9. `deposit` and `balance` never wait for in-flight charges.

Error precedence is specified only where stated above; do not test inputs that break several unrelated rules at once. No persistence, network, timers, or key cleanup schedule is required. Keep the source compact, use the public API in tests, and do not add behavior beyond this contract.
